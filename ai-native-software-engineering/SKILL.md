# AI-native 软件工程规范

## 目标

把 AI 编程从“生成能运行的代码”变成可审查、可验证、可回滚的工程闭环。优先级为：正确性、安全性、简单性、可读性、可测试性、可维护性和可演进性。

最终衡量标准不是新增了多少代码，而是：

> 在尽量少增加系统复杂度的前提下，交付多少经过验证的有效行为。

持续关注三个指标：

- `Context Radius`：完成一次安全修改所需理解的上下文范围。
- `Change Surface Area`：需求影响的模块、文件、契约和数据范围。
- `Verification Cost`：证明修改正确所需的测试、环境和人工参与。

## 工作契约

### 1. 先明确约束，再实现

开始修改前，先定位实际代码库、项目级指令和相关模块，并明确：

- 需求的验收标准：正常行为、边界输入、失败行为和兼容要求。
- 业务规则与不变量：什么必须成立，什么永远不能发生。
- 数据 ownership：谁拥有状态，谁能读，谁能写。
- 受影响的接口、事件、消息、文件格式和数据库 schema。
- 哪些现有行为必须保持不变。

对不确定的 API、库版本、配置或运行行为不要猜测；说明假设，并在可能时查阅仓库或官方文档确认。不要编造不存在的 API、命令或测试结果。

### 2. 按变化原因划分模块

把会因同一原因一起变化的代码放在一起，把因不同原因变化的代码隔离。优先按业务领域组织边界，如 `orders/`、`payments/`、`pricing/`；技术分层可以存在于领域内部，但不应让一个小业务变化被迫横跨整个 `controllers/services/repositories` 树。

模块应高内聚、低耦合、信息隐藏，对外提供最小且稳定的接口。不要把“执行顺序相邻”误当成“应该独立”；流程阶段只有在拥有独立规则、变化轴或故障隔离价值时才成为边界。

### 3. 控制复杂度与修改范围

选择满足需求的最简单正确实现：少抽象、少依赖、少状态、短数据流、明确输入输出。不要为假想未来提前创建 `Factory`、`Manager`、`Service`、`Repository`、事件总线或微服务。

只有当隔离变化或故障的收益大于接口、协调、序列化、错误处理和测试成本时，才增加边界。一个普通需求若异常扩大 `Change Surface Area`，先检查 ownership、依赖方向和架构泄漏，再继续堆代码。

优先清晰而非炫技：简单控制流、早返回、明确命名、小而完整的函数。代码解释“做什么”，注释只解释“为什么这样做、为何不能采用明显替代方案”。把纯计算与数据库、网络、文件等副作用分开，并尽量减少 shared mutable state。

### 4. 契约和数据必须稳定演进

公共 API、模块接口、事件 schema、消息格式、文件格式和数据库 schema 都是契约。优先 additive change；破坏性变化必须说明版本、消费者影响、弃用期、迁移方案和回滚方案。消费者应能安全处理未知字段，序列化不应依赖字段顺序。

数据库变更不能当作普通代码重构。考虑既有数据、前后兼容、索引和锁风险、部分迁移、数据修复及不可逆性。高风险迁移优先采用：

`Expand → Compatible Deploy → Migrate → Verify → Contract`

迁移应尽量可暂停、可重试、可监控、可校验和幂等。代码可以回滚，数据未必可以回滚。

### 5. 安全默认开启

所有外部输入默认不可信。根据技术栈落实 schema validation、参数化查询、输出 escaping、路径遍历防护、授权和最小权限；为外部请求设置 timeout，并按场景设计 retry、backoff、idempotency 和 rate limit。不得硬编码 secret，不得把 secret 写入日志，不得使用 `eval`/`exec` 绕过安全边界，不得静默吞异常。

新增依赖前先检查标准库和现有依赖；说明必要性，锁定版本，清理未使用依赖，并检查已知漏洞和 breaking changes。

### 6. 测试是长期记忆

测试优先保护需求行为、契约和不变量，而非绑定私有实现细节。至少考虑 happy path、边界输入、非法输入和失败路径；按风险选择 unit、integration、contract 或 end-to-end 测试。测试应尽量确定、隔离、可重复，避免无控制地依赖当前时间、随机数、外部网络或共享环境。

修复有意义的 bug 时遵循：

`复现 → 添加失败的 regression test → 修复 → 通过 → 保留测试`

AI 同时写实现和测试时，额外审查测试是否只是证明当前实现，而没有验证真实需求。关键路径应有独立的验收标准或批判性 review。

### 7. AI 修改后完成验证闭环

修改后自动执行仓库已有且适用的检查，通常包括：

`Format → Lint → Type Check → Unit Tests → Integration/Contract Tests → Build → Security Checks`

根据项目实际情况裁剪，不要虚构不存在的脚本。检查失败时先读取真实错误，定位根因，做最小修复并重跑受影响检查；不要用删测试、放宽类型、吞异常或跳过检查来制造“通过”。区分“通过”“失败”“未运行”“受环境阻塞”，不能把未运行说成已验证。

完成实现后再做一次独立的批判性审查，重点检查：需求遗漏、边界条件、数据竞争、资源泄漏、错误处理、安全边界、兼容性、无谓复杂度和回滚路径。

### 8. 按风险分配自主权

- 低风险、可逆、可验证的本地修改：AI 可以直接执行并验证。
- 中风险、可验证的变更：AI 执行，提供测试证据和残余风险。
- 高风险或不可逆操作：AI 只准备方案、迁移/回滚步骤和验证方式，涉及生产数据删除、支付、权限、secret、破坏性 schema 变更和 production deployment 时，先取得人工确认。

不要因为“用户要求完成任务”就推断获得了额外的生产权限或破坏性操作授权。

### 9. 删除功能也要删除复杂度

删除功能时同步检查 dead code、公共 API、配置、feature flag、数据库字段、测试、依赖、文档、兼容分支、监控和告警。不要只隐藏入口，也不要把废弃路径永久保留成“以后可能有用”的负债。

### 10. 小步交付并保持可审查

遵循 `Small Diff, Clear Intent`。不要把功能开发、大规模重构、全局格式化和依赖升级混入同一变更。关键生产流程应具备结构化日志、metrics、错误上报，必要时增加 tracing，并能够回答：哪里出错、影响多少、从什么时候开始。

## 完成时的输出

简要说明：改了什么、为什么这样分边界、验收标准和不变量是什么、运行了哪些检查及结果、哪些检查未运行或受阻、剩余风险和需要人工决定的事项。只报告已观察到的事实，不把推测、静态阅读或生成代码当成运行验证。

## 最高原则

> 架构约束复杂度；契约稳定边界；不变量守住正确性；测试保存经验；删除控制熵增；自动化闭合验证；人负责目标、权衡和不可逆决策。
